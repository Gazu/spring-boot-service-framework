# OpenAPI Project Scaffolding

The project generator creates a new Spring Boot service that depends on one
generated OpenAPI server API artifact and exposes explicit hexagonal package
boundaries. It is a one-time bootstrap tool: it does not own, synchronize, or
regenerate application code after the project is created.

Use scaffolding when starting a service implementation. Use the
[OpenAPI Gradle plugin](plugin-reference.md) when the required outcome is only
models, server API, or client artifacts.

## Generation Model

The generator accepts exactly one contract source:

- an OpenAPI YAML or JSON document; or
- a framework-generated server API JAR.

Spring Initializr creates the Gradle and Spring Boot base project. The framework
then adds the server API dependency, delegate adapters, hexagonal packages,
configuration, tests, and an embedded contract copy.

The input contract remains the transport boundary. The generator does not infer
domain entities, use cases, outbound ports, persistence, or business logic from
OpenAPI schemas.

## Prerequisites

- Java 21;
- the repository Gradle wrapper when invoking the provided task;
- a valid OpenAPI `3.0.x` or `3.1.x` document, or a server API JAR generated by
  this framework;
- the server API artifact available from `mavenLocal()` or the configured
  contract repository before the generated project is built.

For document input, generate and publish the server API artifact first by
following [Artifact Generation](generation.md) and
[Artifact Publishing](publishing.md). Scaffolding references that artifact; it
does not publish it.

## Gradle Task

Run the project generator from this repository:

```bash
./gradlew :spring-boot-service-framework-project-generator:generateHexagonalProject \
  -Pspec=docs/openapi/warehouse-inventory-catalog.yaml \
  -Poutput=build/generated/warehouse-inventory-service \
  -PcontractRepository=build/repository/openapi
```

Use a generated server API JAR instead of a document:

```bash
./gradlew :spring-boot-service-framework-project-generator:generateHexagonalProject \
  -PapiJar=/path/to/warehouse-inventory-catalog-server-api-1.0.0.jar \
  -Poutput=build/generated/warehouse-inventory-service \
  -PcontractRepository=https://artifactory.example.com/maven-releases
```

Exactly one of `-Pspec` and `-PapiJar` is required. `-Poutput` is always
required. Relative source, output, JAR, and local repository paths are resolved
from the root repository.

### Gradle Properties

| Property | CLI option | Required | Default or behavior |
|---|---|---:|---|
| `spec` | `--spec` | Conditional | OpenAPI YAML or JSON source; mutually exclusive with `apiJar`. |
| `apiJar` | `--api-jar` | Conditional | Framework server API JAR; mutually exclusive with `spec`. |
| `output` | `--output` | Yes | No default. Target project directory. |
| `group` | `--group` | No | `com.smbtech`. |
| `artifact` | `--artifact` | No | `<normalized-contract-id>-service`. |
| `packageName` | `--package` | No | `<group>.services.<contract-id-without-hyphens>`. |
| `applicationName` | `--application-name` | No | Contract ID converted to a Java type plus `Application`. |
| `projectVersion` | `--project-version` | No | `0.1.0-SNAPSHOT`. |
| `frameworkVersion` | `--framework-version` | No | Framework version embedded in the project-generator artifact. |
| `springBootVersion` | `--spring-boot-version` | No | Spring Boot version embedded in the project-generator artifact. |
| `contractGroup` | `--contract-group` | No | Source metadata, or `com.smbtech.contracts` for document input. |
| `contractArtifact` | `--contract-artifact` | No | Source metadata, or `<normalized-contract-id>-server-api` for document input. |
| `contractVersion` | `--contract-version` | No | Source metadata or `info.version`. |
| `contractApiPackage` | `--contract-api-package` | No | `com.smbtech.contracts.<contract-id-without-hyphens>.api` for document input. Not allowed for JAR input. |
| `contractRepository` | `--contract-repository` | No | No additional repository. Paths become `file:` repository URIs. |
| `force` | `--force` | No | `false`; when `true`, replaces a non-empty disposable target. |

An artifact ID must use lowercase alphanumeric segments separated by hyphens.
Packages must be lowercase Java package names, the application name must be a
valid Java type, and the contract version must be SemVer/Maven compatible.

## Command-Line Interface

The published module exposes
`com.smbtech.serviceframework.project.generator.ProjectGeneratorCli` as its
application entry point. Its direct syntax is:

```text
project-generator --spec=<openapi.yml> --output=<directory> [options]
project-generator --api-jar=<server-api.jar> --output=<directory> [options]
```

Run `project-generator --help` for the option list. Unknown, duplicated, or
blank options fail with exit code `2`. Generation failures use the same exit
code and write a diagnostic message to standard error.

## Java API

Applications and build tools can invoke the small public API directly:

```java
Path contract = Path.of("contracts/warehouse-inventory-catalog.yaml");
Path output = Path.of("build/generated/warehouse-inventory-service");

ProjectGenerationRequest request =
        ProjectGenerationRequest.builder(new OpenApiDocumentSource(contract), output)
                .groupId("com.example")
                .contractRepository(URI.create("https://repo.example.com/releases"))
                .build();

GeneratedProject project = HexagonalProjectGenerator.create().generate(request);
```

Use `ServerApiJarSource` instead of `OpenApiDocumentSource` for JAR input.
`GeneratedProject` returns the generated directory, normalized contract ID,
contract version, server API Maven coordinate, and delegate interface names.
Invalid input or generation failures raise `ProjectGenerationException`.

The supported library API is:

- `HexagonalProjectGenerator`;
- `ProjectGenerationRequest` and its builder;
- `ProjectContractSource`;
- `OpenApiDocumentSource`;
- `ServerApiJarSource`;
- `GeneratedProject`;
- `ProjectGenerationException`.

`ProjectGeneratorCli` is public technical infrastructure because Java requires
the application entry point to be accessible. Invoke it as a command; do not
couple application code to the launcher class.

Contract parsing, name resolution, Spring Initializr composition, and project
contributors are implementation details, not extension points.

## Contract Source Rules

### OpenAPI Document

Document input must parse as OpenAPI `3.0.x` or `3.1.x` and declare:

- nonblank `info.title`;
- nonblank `info.version`;
- at least one path.

The title is normalized into the contract ID. Delegate interface names are
derived from operation tags using OpenAPI Generator's Spring naming. Untagged
operations belong to `DefaultApiDelegate`.

Document input does not inspect a published JAR. Consequently, explicit
`contractGroup`, `contractArtifact`, `contractVersion`, and
`contractApiPackage` overrides must match the server API artifact that the
generated project will consume.

### Server API JAR

JAR input must contain:

```text
META-INF/smbtech/openapi/contract.properties
META-INF/smbtech/openapi/contract.yaml
```

Its metadata must identify `artifact.kind=server-api` or the compatible legacy
value `api`, and the JAR must contain at least one top-level `ApiDelegate`
interface. Contract identity, artifact coordinates, and delegate types are read
from the JAR. `contractApiPackage` cannot override classes already embedded in
the artifact.

## Generated Project

For the warehouse inventory example, the important output is:

```text
warehouse-inventory-catalog-service/
|-- build.gradle
|-- settings.gradle
|-- gradle.properties
|-- gradlew
|-- gradlew.bat
|-- gradle/wrapper/
|-- .gitignore
|-- .gitattributes
|-- README.md
`-- src/
    |-- main/
    |   |-- java/<base-package>/
    |   |   |-- <ApplicationName>.java
    |   |   |-- domain/model/package-info.java
    |   |   |-- application/port/in/package-info.java
    |   |   |-- application/port/out/package-info.java
    |   |   |-- application/service/package-info.java
    |   |   |-- adapter/in/web/<ApiDelegate>Adapter.java
    |   |   |-- adapter/out/package-info.java
    |   |   `-- configuration/package-info.java
    |   |-- openapi/contract.yaml
    |   `-- resources/application.yml
    `-- test/java/<base-package>/
        |-- ApplicationContextTest.java
        `-- HexagonalArchitectureTest.java
```

The generated build uses Java 21 and the selected Spring Boot version. It adds:

- the framework platform;
- logging and error-handling starters;
- `spring-boot-starter-webmvc`;
- the generated server API coordinate;
- Spring Boot Test and ArchUnit for tests;
- `mavenLocal()`, Maven Central, and the optional contract repository.

Each generated delegate adapter is a Spring `@Component` that implements one
server API `ApiDelegate`. The empty implementation intentionally relies on the
generated delegate defaults until application behavior is added.

The original contract is copied to `src/main/openapi/contract.yaml`.
`application.yml` sets the application name and configures error exposure as
`PUBLIC`. Review all generated dependencies and configuration before deploying
the service.

## Hexagonal Boundaries

The scaffold provides locations and enforcement, not application architecture
implementation:

| Package | Responsibility |
|---|---|
| `domain.model` | Business state, values, and invariants without framework dependencies. |
| `application.port.in` | Inbound use-case contracts. |
| `application.port.out` | Outbound dependency contracts. |
| `application.service` | Use-case orchestration and application behavior. |
| `adapter.in.web` | Generated OpenAPI delegate implementations and web translation. |
| `adapter.out` | Persistence, messaging, and downstream integrations. |
| `configuration` | Spring composition and application configuration. |

`HexagonalArchitectureTest` enforces three initial rules:

- domain code does not depend on Spring, application, adapters, or
  configuration;
- application code does not depend on adapters or configuration;
- inbound adapters do not depend on outbound adapters.

These rules are a minimum boundary. The generated project owns them after
creation and may add stricter application-specific rules.

## Output Safety

Generation accepts a missing or empty target directory. It rejects a non-empty
target unless `force` or `--force` is enabled.

Force mode recursively deletes the target before generation. The generator
refuses to replace a filesystem root or the current user's home directory, but
force mode must still be limited to disposable generated directories. Never use
it against an existing service repository.

## Contract Evolution

The generator does not merge later contract changes into the service. After the
initial scaffold:

1. publish the new server API version;
2. update the generated project's server API dependency;
3. compile to identify delegate and model changes;
4. adapt application-owned adapters and tests manually;
5. run the generated build and contract tests.

Do not rerun scaffolding over the application. Use
[Contract Versioning](versioning.md) and
[OpenAPI Contract Testing](../openapi-contract-testing.md) for ongoing contract
evolution.

## Validation

Validate the generator module and a generated consumer with:

```bash
./gradlew :spring-boot-service-framework-project-generator:check
./gradlew :spring-boot-service-framework-project-generator:scaffoldingCompatibilityCheck
```

`scaffoldingCompatibilityCheck` publishes the required framework and OpenAPI
artifacts to a temporary Maven repository, generates a fixture from the
warehouse inventory contract, and runs the generated project's `clean test`.
That test compiles the delegate adapters, starts the Spring context, and executes
the ArchUnit rules.

The repository `compatibilityCheck` lifecycle includes this scaffolding check.

## Troubleshooting

| Failure | Cause | Resolution |
|---|---|---|
| `Provide exactly one of ... spec ... apiJar` | Both contract inputs or neither were provided. | Select one source. |
| `Contract source does not exist` | The document or JAR path cannot be resolved. | Use an existing file and check path resolution from the repository root. |
| `embedded contract metadata is missing` | The JAR was not produced as a framework server API artifact. | Use the generated `server-api` JAR, not models or client JARs. |
| `contains no ApiDelegate interfaces` | The JAR has no generated server delegate contract. | Regenerate the server API from a contract with operations. |
| `Could not find ... server-api` | The generated project cannot resolve its contract dependency. | Publish locally or configure `contractRepository` with the correct coordinate. |
| `Output directory is not empty` | The target contains files and replacement is disabled. | Choose an empty target; use force only for a disposable scaffold. |
| `contractApiPackage cannot override` | A JAR source already fixes its compiled package. | Remove the override or generate from the source document. |
| ArchUnit test failure | Application code crossed a generated dependency boundary. | Move the dependency behind the appropriate port or adapter. |

For contract parsing, generation, and publication failures, continue with
[OpenAPI Validation](validation.md) and the repository
[Troubleshooting Guide](../troubleshooting.md).
