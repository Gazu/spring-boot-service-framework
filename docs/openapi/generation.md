# OpenAPI Artifact Generation

The OpenAPI Gradle plugin turns each discovered or explicitly configured
OpenAPI 3.0 or 3.1 contract into independent model, Spring MVC API, and
declarative client artifacts.
OpenAPI Generator produces the Java sources; the framework owns artifact
separation, package conventions, compilation, metadata, and integration with
the REST client starter.

For a first executable workflow, complete
[OpenAPI Getting Started](getting-started.md) before using this reference.

## Generation Pipeline

Each enabled contract follows the same build-time pipeline:

```text
OpenAPI document
  -> contract and coordinate validation
  -> source generation by artifact kind
  -> Java 21 compilation
  -> deterministic contract metadata
  -> binary JAR and sources JAR
  -> Maven publication variants
```

Generation never modifies the source contract or application source code.
Generated sources and classes remain build outputs.

## Artifact Set

Given this effective identity:

```text
group:   com.smbtech.contracts
name:    warehouse-inventory-catalog
version: 1.0.0
```

the plugin creates:

| Kind | Coordinate | Primary consumer |
|---|---|---|
| Model | `com.smbtech.contracts:warehouse-inventory-catalog-jdk21-model:1.0.0` | Providers and consumers sharing transport schemas |
| API | `com.smbtech.contracts:warehouse-inventory-catalog-jdk21-api:1.0.0` | Spring MVC application implementing generated delegates |
| Client | `com.smbtech.contracts:warehouse-inventory-catalog-jdk21-client:1.0.0` | Applications invoking the API declaratively |

The effective group defaults to `com.smbtech.contracts`; name and version
come from normalized `info.title` and `info.version`. The `jdk21` segment is a
fixed part of the artifact ID for the Java 21 toolchain. Identity and version
rules are owned by [OpenAPI Contract Versioning](versioning.md); per-contract
configuration is defined in the
[OpenAPI Gradle Plugin Reference](plugin-reference.md).

## Package Layout

For artifact base name `warehouse-inventory-catalog`, default Java packages are:

```text
com.smbtech.contracts.warehouseinventorycatalog.v1.model
com.smbtech.contracts.warehouseinventorycatalog.v1.api
com.smbtech.contracts.warehouseinventorycatalog.v1.client.httpinterface
com.smbtech.contracts.warehouseinventorycatalog.v1.client.openfeign
```

The normalized artifact name loses hyphens when forming the base Java package.
The `v1` segment comes from the major component of `info.version: 1.0.0`.
`basePackage` is the supported unversioned root override. Kind-specific package
properties are compatibility inputs and, when configured, must resolve to this
same versioned structure. Package identity affects generated bytecode and must
remain stable for an already published contract version.

## Model Artifact

The models JAR contains transport types generated from `components.schemas` and
inline operation schemas:

- object DTOs;
- string and numeric enums;
- nested and referenced schemas;
- typed arrays and maps;
- Java temporal and scalar types selected by the pinned generator;
- Jackson property, creator, value, inclusion, and null-handling annotations;
- Jakarta Validation constraints derived from required fields and schema
  limits.

Examples of preserved schema constraints include `required`, `minimum`,
`maximum`, `minLength`, `maxLength`, `pattern`, `minItems`, and `maxItems`.
Validation annotations are generated on the corresponding fields and accessors.

Generated model annotations use `com.fasterxml.jackson.annotation`; this is the
stable Jackson annotation namespace even though Spring Boot 4 uses the Jackson
3 mapper under `tools.jackson`.

The models artifact does not contain controllers, delegates, HTTP clients, mock
routes, application services, or domain entities. Generated DTOs are transport
contracts and do not define the consuming application's domain model.

Its published API dependencies are:

- Jackson annotations;
- Jakarta Validation API;
- Spring Context annotations;
- Hibernate Validator.

## API Artifact

The API JAR contains Spring MVC transport contracts generated from paths,
operations, parameters, request bodies, responses, and tags. For an untagged
contract such as the repository example, generation produces:

```text
DefaultApi
DefaultApiDelegate
DefaultApiController
ApiUtil
```

The generated API carries Spring MVC mappings and validation annotations. The
controller delegates each operation to an `ApiDelegate` implementation. A
provider application supplies that delegate as a Spring bean; the generated
controller remains transport glue and should not contain application logic.

The API artifact:

- contains API interfaces, delegate interfaces, controllers, and required
  transport support;
- uses `ResponseEntity` for generated operation results;
- supports tag-based API grouping through OpenAPI Generator;
- depends on the matching models artifact at the same group and version;
- publishes Spring Web and Jakarta Servlet requirements as Maven dependencies;
- does not duplicate model classes or contain a business implementation.

The generated base-path property is a transport setting. Applications may
configure it without changing generated sources.

## Client Artifact

The client JAR is a contract-only boundary with two package families:

```text
<basePackage>.v<major>.client.httpinterface
<basePackage>.v<major>.client.openfeign
```

Each interface preserves the contract's HTTP method, path, parameters, content
types, and model types. Spring HTTP Interfaces use Spring `@HttpExchange`
annotations; OpenFeign interfaces use the corresponding Spring Cloud OpenFeign
annotations. Both variants use the same simple interface name in their distinct
packages. For example, an untagged contract produces `DefaultApi` in both
client packages.

The framework adds this annotation to every generated HTTP Interface:

```java
@HttpApiClient("warehouse-inventory-catalog")
```

The annotation value is the normalized artifact base name and therefore must
match the REST client configuration key in the consuming application.

The matching OpenFeign interface carries a direct annotation without an
embedded endpoint URL or generated client configuration:

```java
@FeignClient(
    name = "warehouse-inventory-catalog",
    contextId = "warehouse-inventory-catalog-v1-DefaultApi"
)
```

The client name remains the stable configuration key. The context ID includes
the API major and interface name, making every generated API family distinct.

The client artifact:

- contains interfaces and no HTTP transport implementation;
- depends on the matching models artifact at the same group and version;
- depends on Spring Web for HTTP interface contracts;
- depends on the framework REST client starter that creates the proxy;
- does not expose Spring Cloud OpenFeign transitively;
- does not contain controllers, delegates, model classes, authentication
  secrets, endpoint URLs, or application configuration.

Authentication, TLS, headers, resilience, observability, and base URLs remain
runtime concerns of the consuming application and the REST client starter.
An application using the OpenFeign package must add
`spring-cloud-starter-openfeign` and use Spring Cloud `2025.1.2` or newer in the
`2025.1.x` line with Spring Boot 4.1.

Client generation runs both interface generators and merges their output into
the same `-jdk21-client` binary and sources JARs. It does not generate
`*ApiClient` wrapper interfaces or `ClientConfiguration` classes.

## Artifact Dependency Rules

```text
model
  ^
  +-- api
  +-- client -- spring-boot-service-framework-starter-rest-client
```

Models may be generated alone. API and client generation require models
to be enabled because both artifacts reference generated model types. The
plugin rejects configurations that enable API or client while disabling models.
At least one artifact kind must remain enabled.

Global defaults apply to every specification and can be overridden per
contract:

| Kind | Global flag | Per-contract flag | Default |
|---|---|---|---|
| Models | `publishModels` | `specs.<name>.publishModels` | `true` |
| Server API | `publishServerApi` | `specs.<name>.publishServerApi` | `true` |
| Client | `publishClient` | `specs.<name>.publishClient` | `true` |

These flags control generation and publication together. They do not merely
hide an already generated artifact.

## Generated Outputs

With default directories, generation writes:

| Output | Location |
|---|---|
| Generated Java sources | `build/generated/smbtech-openapi/<spec-name>/<kind>/src/main/java` |
| Compiled classes | `build/classes/smbtech-openapi/<spec-name>/<kind>` |
| Generated metadata | `build/generated/smbtech-openapi-metadata/<spec-name>/<kind>` |
| Binary and sources JARs | `build/libs/smbtech-openapi` |

`outputDirectory` controls the generated source root. Compiled classes,
metadata staging, and final JAR directories are framework-managed build outputs.
Do not commit any of these directories.

Every JAR is assembled with stable entry order and without preserved file
timestamps. A matching sources JAR contains generated Java, while the binary JAR
contains compiled classes plus embedded contract metadata.

## Embedded Contract

Each binary artifact embeds the exact input document and `contract.properties`
in a compatibility location and a collision-free contract/version location:

```text
META-INF/smbtech/openapi/contract.yaml
META-INF/smbtech/openapi/contract.properties
META-INF/smbtech/openapi/contracts/<name>/<version>/contract.yaml
META-INF/smbtech/openapi/contracts/<name>/<version>/contract.properties
```

The versioned location allows multiple generated contracts on the same
classpath. Metadata includes artifact identity, contract identity, SHA-256,
framework version, generator version, and Spring Boot version. The exact key
contract is frozen in the
[Current Behavior Inventory](../openapi-behavior-inventory.md).

## Generation Tasks

| Task | Scope |
|---|---|
| `smbtechOpenApiGenerateModels` | Generate source sets for every enabled models artifact |
| `smbtechOpenApiGenerateServerApi` | Generate source sets for every enabled server API artifact |
| `smbtechOpenApiGenerateClient` | Generate source sets for every enabled client artifact |
| `smbtechOpenApiAssemble` | Generate, compile, add metadata, and package every enabled artifact |

Use the kind-specific tasks while inspecting generated sources. Use
`smbtechOpenApiAssemble` for a complete local build. Maven publication is a
separate stage documented in
[OpenAPI Artifact Publishing](publishing.md).

The complete aggregate task contract and build lifecycle wiring are defined in
the [OpenAPI Gradle Plugin Reference](plugin-reference.md).

## Generated Code Policy

Generated sources are immutable build products:

- change the OpenAPI document to change models or operations;
- change public plugin conventions or versioned templates for framework-wide
  behavior;
- never patch files below `build/generated/smbtech-openapi`;
- never copy generated transport types into application source;
- do not add business logic to generated controllers or clients;
- increment `info.version` when a generated public contract changes.

OpenAPI Generator and template upgrades can change generated source or bytecode.
The framework pins both and verifies generated consumers and reproducibility
before accepting an upgrade.

## Validation

Run the generation and consumer boundary checks with:

```bash
./gradlew smbtechOpenApiAssemble
./gradlew smbtechOpenApiConsumerTest
./gradlew smbtechOpenApiReproducibilityCheck
./gradlew smbtechOpenApiCompatibilityCheck
```

The compatibility lifecycle verifies artifact separation, required Maven
dependencies, embedded contracts, generated delegate and HTTP interface shapes,
consumer compilation, and deterministic archives.

The immutable external contract is recorded in
[ADR 0002](../adr/0002-openapi-artifact-contract.md). GitHub Packages change
detection and automatic publication are intentionally outside Phase 3.

For the complete configuration, document, coordinate, and compatibility task
model, use [OpenAPI Validation](validation.md).

Return to the [OpenAPI Portal](index.md) for getting started, publication,
versioning, testing, mocks, and scaffolding.
